# Brief 分析方法

仅在分析 Brief、材料或创作方向时读取。

## 1. 建立素材与来源清单

先确认用户实际提供了什么，而不是只看正文：

| 来源 | 常见内容 | 检查重点 |
|---|---|---|
| Brief / PDF / 文档 | 产品介绍、主推功能、必提点、交付要求 | 标题层级、批注、表格、页脚、小字限制 |
| 聊天补充 / 邮件 | 最新改动、口头硬要求 | 日期、发送方、是否覆盖旧版本 |
| 官网 / 活动页 | 当前功能、定价、产品术语 | 只证明产品事实，不自动构成 campaign 要求 |
| 图片 / 截图 / GIF | UI、Logo、视觉规范、操作步骤 | 是否为最新版、文字是否可读 |
| 参考视频 | Hook、节奏、镜头、演示方式 | 甲方让参考的是哪一层，而非笼统模仿 |
| 用户过往内容 | 账号口吻、结构、出镜和录屏习惯 | 只在用户提供或允许分析时使用 |

每项标记：`已核验`、`部分核验`、`无法访问`、`未提供`。如果链接要求登录或视频无法播放，保留链接和甲方说明，但不要声称已分析内容。

## 2. 区分产品全貌与本次推广任务

分别回答：

- 产品解决什么核心问题？
- 产品完整能力有哪些？
- 这次 Brief 点名要推哪一个功能、场景或活动？
- 用户应记住的唯一一句话是什么？
- 哪些资料只是品牌背景，放进视频反而稀释重点？

用“输入 → 产品做什么 → 产出/变化”的形式描述功能，优先写用户可观察的动作，不照抄品牌黑话。若无法判断主推项，列出候选及各自证据，并标 `[UNKNOWN]`。

## 3. 提取要求并分配 R 编号

将要求拆到最小可验证单元。不要把“展示产品、讲功能、带 CTA”合成一条。

建议字段：

| ID | 标签 | 要求 | 来源定位 | 验收方式 | 对创作的影响 |
|---|---|---|---|---|---|
| R1 | `[REQUIRED]` | 示例：口播产品全名 | `[S1 p.2]` | 逐字稿中可找到 | 首次介绍时自然带出 |

重点扫描：

- 产品名、Slogan、功能名及指定拼写/读法
- 必须演示的输入、操作步骤和输出结果
- 必须出现的 Logo、页面、字幕、链接、优惠码、话题、口播和 CTA
- 平台、视频时长、画幅、语言、出镜方式、发布日期和修改节点
- 禁词、竞品、素材版权、数据声称、承诺性话术和画面禁区
- “建议”“可选”“示例”是否被误读成强制项

## 4. 分析参考视频

先判断参考任务：甲方是在参考 Hook、结构、功能演示、视觉、人物状态、节奏、转场、结果展示，还是 CTA？若 Brief 没说明，标 `[UNKNOWN]`。

每条可访问视频记录：

- 来源与时长
- 甲方指定用途
- 时间段结构：每段的目的、画面和信息
- 最值得迁移的机制
- 与用户账号不匹配的部分
- 版权或素材复用风险
- 可迁移到哪个创作方向

“像这条”不是分析结果。必须翻译成可执行动作，例如“前 2 秒先展示生成结果，再回到输入步骤”。

## 5. 生成真正不同的创作方向

通常给 3 个；素材极少或约束很强时可给 2 个。优先从以下叙事机制中选互不重复的组合：

- **工具发现型**：发现 → 为什么值得看 → 操作 → 结果 → 评价
- **痛点实验型**：提出可验证问题 → 现场实验 → 结果揭晓
- **旧方法 vs 新方法**：旧流程成本 → 新流程演示 → 差异
- **结果倒叙型**：先看成果 → 追溯怎么做到 → 使用边界
- **任务挑战型**：限定时间或目标 → 用产品完成 → 复盘

每个方向必须说明：

1. 一句话命题与首句 Hook
2. 叙事链路
3. 主要展示哪个功能和结果
4. 覆盖哪些 `R#`
5. 为什么适合当前账号与平台
6. 广告感、证据、拍摄成本或合规风险
7. 借鉴参考视频的具体机制

推荐时给出理由与取舍，不要只写“最推荐 A”。方向不能承诺 Brief 没有证据支持的结果。

## 6. 只问高价值问题

将未知项分为：

- **阻塞**：不回答就无法确定产品、核心推广功能、必需 CTA 或禁区。
- **高影响**：会明显改变 Hook、脚本结构、拍摄量或交付合规。
- **可暂定**：可以先用明确占位符完成草稿。

第一阶段问题清单优先展示阻塞与高影响项，通常不超过 7 个。不要询问已经能从材料找到的内容，也不要为了完美信息而阻止用户先看创作方向。
